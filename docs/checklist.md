# FinClarity — Build Checklist

## Build Preferences

- **Build mode:** Step-by-step
- **Comprehension checks:** Yes — after each item, a short question to confirm the piece makes sense before moving on
- **Git:** Commit after each item with message: `Complete step N: [title]`
- **Verification:** Yes — run the app after each item and confirm what you see before moving to the next
- **Check-in cadence:** Balanced — PM-relevant explanations of what was just built and how it connects, without going deep into code detail

## Row Level Security — critical finding (2026-08-05)

- [x] **20. Add missing Row Level Security policies before deploying**
  Context: the old Supabase project (referenced by items 1–19) was deleted at some point and replaced with a new one (see process notes for that migration). `supabase/schema.sql` was never updated to include RLS policies — it never had any, on either project. The app has no service-role key anywhere (`lib/supabase/server.ts` and `lib/supabase/client.ts` both use only the public anon key); every API route authenticates as the calling user's own session and relies entirely on RLS to scope access.
  What was found: on the new project, RLS is **enabled** on `users` (confirmed via a `403 new row violates row-level security policy` when a freshly-created anonymous user tried to insert their own row) but has **zero policies** — meaning even a user's own legitimate self-access is denied by default. Two freshly created independent anonymous sessions could not read their own `public.users` row, could not read each other's, and could not write. Cross-user data leakage was **not** observed (good), but the app is currently **non-functional** for any authenticated write/read against `users`/`statements`/`transactions`/`monthly_reports`/`check_ins` on the new project — including the `users` upsert fallback that both `/api/statements/upload` and `/api/user` depend on, and the entire delete-account flow.
  What to build: Run the new "Row Level Security" section added to `supabase/schema.sql` against the live project via the Supabase SQL editor — self-access-only policies (`auth.uid() = id` / `auth.uid() = user_id`) for all 6 tables, plus a public-read policy for the non-user-scoped `exchange_rates` table.
  Acceptance: after running the SQL, a freshly authenticated user can read/write their own rows in all 6 tables, and cannot read or write another user's rows (re-run the two-anonymous-session cross-access test to confirm).
  Verify: see the cross-session curl test used to diagnose this — create two independent anonymous sessions, confirm each can read/insert/update only their own `users` row and neither can see the other's.
  Verified (2026-08-05): policies run against the live project. Re-ran the cross-session test with two fresh anonymous users: self-access (read/insert-via-upsert/update) works; cross-user UPDATE and DELETE both affected 0 rows (confirmed target row unchanged afterward); an INSERT impersonating another user's `user_id` was hard-blocked with a 403 RLS violation; the anon key alone (no session) still can't read anything.
